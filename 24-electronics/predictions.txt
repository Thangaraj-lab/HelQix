E1 — DC analysis (written before any E1 code)
---------------------------------------------
Prediction:
- The hand-calculated divider, bridge, Thevenin/Norton, superposition and
  10-node ladder cases will agree to better than 1e-12 relative with sparse
  MNA in float64, i.e. inside the 1e-9 target.
- The dominant risk is sign convention on current sources and VCVS control

E2 — Transient / AC / nonlinear (written before any E2 code)
------------------------------------------------------------
Prediction:
- Trapezoidal RC charge at h = T/200 will be within 0.02% of the analytic
  curve; backward Euler will be within 0.5% only at the same step, so the
  0.5% target is reachable with both methods at modest step counts.
- RLC resonance with Q around 5 will be within 0.2% of 1/(2*pi*sqrt(LC))
  when the sweep has 200 points/decade plus bisection refinement.
- Newton on a diode with series resistance will converge in under 15
  iterations with damping; without damping it will overflow exp() on a
  direct 5 V step. Expect to need a voltage limiter.
- MOSFET level-1 saturation current will match the formula to float64
  round-off (it is the same formula) inside 1e-12.
- Op-amp gain target 0.1% is easy for the finite-gain model; the ideal
  model needs a nullor constraint, not a 1e9 VCVS, or the matrix becomes
  badly conditioned.
- AC cutoff search by bisection will hit 1% easily; a 20-point/decade grid
  alone may miss by 1–2% near the knee.
- Risk: adaptive stepping can reject forever near a switching event.
  Mitigation: minimum step and a hard max_steps report.
- Expected suite runtime: under 10 s.

R2 Phase 3 item 4 - E7 live probe (written before writing the probe)
--------------------------------------------------------------------
Intent: one process, no threads, no network. A seeded sensor trace is sent
twice - once through the serial pair, once through the broker - into a
consumer that checks every delivered reading against the sensor's reported
value. Each scenario injects one fault on the receiving side and compares the
observed counters with an independent prediction from the same seed.

Hand-derived expectations for n = 120 readings:
- clean: order 0..119 on both channels; received 120, all fault counters 0.
- drop p=0.5, seed s: every frame is consumed once in order and dropped with
  one draw of random.Random(s); received + dropped = 120, and the delivered
  index list equals the independent prediction exactly, on both channels.
- corrupt p=0.5: delivered + corrupted = 120, every delivered payload passes
  the frame/bus checksum and carries the exact quantized value.
- delay_s=0.05: a probe read with a 0.01 s timeout must raise IOTimeoutError;
  after that all 120 readings arrive in order.
- reorder p=1.0: the receiver swaps each frame with the next one, so the
  order becomes 1,2,...,119,0, reordered = 119, and exactly one first
  delivery is below the running maximum.
- duplicate p=1.0: each reading is delivered twice before the next one, so
  the order is 0,0,1,1,...,119,119, received = 240, duplicated = 120.
- combined (drop/corrupt/duplicate/reorder p=0.1, delay 5 ms): only
  conservation is asserted: unique + dropped + corrupted = 120 and
  received = unique + duplicates, because the five draws interleave.
- two seeds: running the whole probe twice with seed 11 must produce an
  identical JSON report (same sensor trace bytes included), and seed 29 must
  differ, at least in the drop scenario.
- Runtime prediction: under 2 s for all scenarios on both channels.
- Risk: the consumer's drain read adds one timeout counter per scenario; the
  assertions therefore name each counter instead of comparing whole stats.
- Risk: 120 writes may let a 5 ms delay expire before reading starts; the
  combined scenario only relies on conservation, so this cannot break it.

R2 Phase 4a - deterministic routing helper (written before writing it)
---------------------------------------------------------------------
All lengths in millimetres in a 2D plane; obstacles are axis-aligned boxes.
The route is a polyline of axis-aligned segments with every turn replaced by
a circular arc of the wire's bend radius R.
- Straight case: start (0,0), end (100,0), no obstacle. Expect 2 points,
  0 bends, cut length exactly 100, equal to the straight-line distance.
- One right-angle: start (0,0), end (100,60), a wall across the direct
  diagonal that forces a single corner at (100,0) or (0,60). R = 5. Sharp
  polyline length 160; with the corner arc the cut length is
  160 - 2*5 + pi*5/2 = 157.854 (CALCULATED). Bends = 1.
- Around a central obstacle: start (0,0), end (100,0), box (40,-10)-(60,10),
  R = 5, clearance 0. The route must pass at y = +-15 (box edge plus R).
  Expect 4 points, 2 bends, sharp length 130, cut length
  130 - 4*5 + 2*(pi*5/2) = 125.708.
- Blocked direct path: an obstacle spanning the whole gap between the
  endpoints, e.g. a box that reaches beyond both endpoints on every side,
  must give blocked = True with a plain-word reason, not an exception and not
  a route through the box.
- A corner needs at least R mm of leg on each side; a route whose only
  available turn is closer than R to an endpoint must be reported blocked
  rather than drawn with a sharper bend.
- Property: for every routed-case in the nightly property test the cut length
  is at least the straight-line distance, and the same input gives the same
  points twice.
- Risk: the visibility grid uses coordinates start, end and box edges +- R,
  so a path can be forced through a coordinate where the arc touches a box
  corner exactly; the arc is sampled and any sample strictly inside a
  clearance-inflated box rejects the route as blocked.

R2 Phase 4b - harness/0.1 document model (written before writing it)
-------------------------------------------------------------------
A harness document is mechanical data only: connectors with pin positions,
wires that name their circuit nodes and the two pins they run between, bundles,
and axis-aligned obstacles.  The route polyline is COMPUTED by the router from
the two pin positions and the obstacles; a polyline supplied in the input is
refused as an unknown key, and this is stated in the output note.
- Gauge to size: AWG 20 is 0.127 * 92 ** ((36 - 20) / 39) = 0.8118 mm diameter
  and 0.5178 mm^2 area (CALCULATED); the existing awg formula and material
  table are reused from harness.py, not duplicated.
- Colour table: IEC 60757 letters (BK, BN, RD, OG, YE, GN, BU, VT, GY, WH, PK,
  TQ, GNYE) and IEC 60445 roles (L1 brown, L2 black, L3 grey, neutral blue,
  protective earth green-yellow).  Not consulted online here, so REPORTED, and
  an unknown colour name or code is refused listing the known names.
- Route example: pins (0,0) and (500,0), obstacle (200,-40)-(300,40), bend
  radius 6 mm.  Expect the detour at y = -46 (box edge plus radius, lower side
  by the equal-cost rule): legs 46 + 500 + 46 = 592 sharp; cut length
  592 - 4*6 + 2*(pi*6/2) = 586.8496 mm.  Declared length 600 mm gives a
  positive margin of 13.15 mm and route_fits True; declared 500 mm gives
  route_fits False as a reported fact, not an input error.
- Blocked route: a wire whose destination pin is sealed by boxes is reported
  with blocked True, cut length value null and label UNKNOWN; the document
  itself still loads.
- Refusals: wrong version, unknown keys (top level, wire, connector, bundle,
  obstacle), duplicate ids, an unknown pin reference, an unknown bundle, both
  gauge_awg and diameter_mm, gauge outside -20..60, non-positive length or
  bend radius, negative slack, a dot in a connector or pin id (pin references
  use "connector.pin"), obstacle box with x0 >= x1 or y0 >= y1.
- Determinism: the same document produces the same JSON twice.
